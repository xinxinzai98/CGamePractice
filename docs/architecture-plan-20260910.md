# Web 游戏架构重整建议

日期：2026-09-10。此方案已获用户批准，第一轮 Phaser 迁移已完成。当前实现与验收见 [迁移记录](phaser-migration-20260910.md)。以下保留迁移前的评估与分阶段计划。

## 判断

继续以 Web 为发布平台。当前自写 Canvas + DOM 原型适合验证玩法；随着场景切换、二游式界面、动态看板、Boss、双人解谜与持久成长加入，继续把这些需求叠加到单个 app.js / engine.js 会增加耦合和返工。建议冻结当前原型，迁移为 Phaser 4 + TypeScript 客户端；不要再同时扩充所有系统。

## 已确定的产品边界

- 面向任意玩家开放的 Web 小游戏，每房间两人协作；个人练习用于教学、技能与装备试配。
- 固定 16:9，等比缩放和留边；封面 → 点击/滑动 → 登录/注册 → 真实加载进度 → 动态主页。
- 主页为机甲/日系二游风格，驾驶员看板、机体展示、切换与悬浮反馈；创作背景归入角落档案/画廊。
- 入房后选择战役、小关卡、难度、出战角色、技能树、弹种、近战与装备。
- 原作是 EVA 致敬的机器人作战项目，不以普通坦克大战定位。
- 方向键移动；左手管理射击、技能、近战、主动配件、切弹与交互。
- 角色熟练度与有前置/分支/终极互斥的技能树；金币、配件、个人存档；免费补给招募，不锁定基础角色。
- 四战役 × 三小关。教学/前期使用旧场地和素材；后期新机甲、地形、敌人和 Boss。
- 弹种与方向防护借鉴载具游戏的决策感；同步能量、控制与主动配件借鉴技能配合。
- 双人分工解谜与适度操作挑战；Boss 具有预警、同步破盾、输出窗口。
- 当前不部署，先在本地达到满意；最终仍在 CGamePractice 原仓库提交。

## 推荐架构

| 层 | 建议 | 职责 |
| --- | --- | --- |
| 游戏场景 | Phaser 4 + TypeScript | 场景切换、WebGL渲染、角色精灵、镜头、粒子、输入、音频、固定比例 |
| 账户与菜单界面 | TypeScript + React，叠加在统一游戏舞台 | 登录、个人资料、房间准备、树、仓库、招募；不以 React 驱动逐帧战斗 |
| 客户端工程 | Vite | 模块化构建、开发热更新、代码拆包、资产引用 |
| 共享模拟 | 独立 TypeScript 包 | 伤害、弹种、技能、冷却、能量、Boss状态机、合作机关、数据校验；不依赖DOM/Phaser |
| 房间服务器 | 保留 Node.js + WebSocket，逐步转 TypeScript | 服务器判定、固定tick、输入验证、快照、重连 |
| 个人档案 | SQLite + 清晰服务层 | 账号、成长、背包、配装、金币/补给交易；从JSON原型事务性迁移 |
| 角色动画 | 专用角色动画资产管线 | 看板可选Live2D；战斗可选骨骼动画或规范图集；先做一个合格样板 |
| 地图与数值 | 开发用结构化数据 | 任务、刷怪、机关、Boss阶段、奖励、装备、技能；不恢复玩家地图工坊 |

客户端状态流程：Boot → Cover → Auth → Lobby → Briefing → Battle / Practice → Result。每个场景负责自身资源与退出清理，公共状态不挂在全局脚本上。HTML界面与游戏画布共用一个16:9舞台、同一套缩放与焦点规则。

服务端继续作为联机权威。Phaser负责表现，不能让客户端物理结果直接决定金币、命中、胜负或档案。

## 动画与美术的真实约束

引擎能改善场景、渲染和动画管理，但不能把单张PNG自动变成专业Live2D模型。自然头发、手臂和身体运动，需要拆分部件、补齐遮挡区域、制作变形网格/骨骼并调节物理参数。当前新增的单图WebGL网格摆动只能作原型，尚未浏览器视觉验收，不能宣称为Live2D成品。

图像生成适合主视觉、概念、图标和静态贴图；战斗方向图集仍需统一视角、锚点、格尺寸、颜色、轮廓和特效遮挡规则。当前红蓝新机甲图集生成结果为一致斜俯视，而非严格正俯视；不能混用不同视角后只靠缩放掩盖问题。

先选定一套完整的参考品质：一个大厅、一个驾驶员、一个战斗机体、一组技能、一个Boss场景。验证满意后再批量补齐资源。

## 现有成果如何处理

保留原始 NewTank / Chartlet，不修改其历史证据。现有新web/server原型单独保留为迁移参考：

- 可复用：游戏规则、技能树与装备数据、房间协议、账户/交易规则、61项逻辑与服务端测试、原始及新生成素材。
- 应重写：集中在app.js里的场景、DOM拼接、资源加载、逐帧渲染、输入与菜单状态交叉逻辑；累积CSS覆盖。
- 应替换：临时画面表现、随意动画切片、单图浮动式看板、缺少按场景加载和资源预算的预加载方案。
- 应升级：JSON个人档案到事务存储；明确存档版本和迁移，保留原文件备份。

当前61项测试通过不代表61项最终游戏功能已完成验收。很多新增图像、封面流程、合作机关和特效还没有完成最终客户端集成与人工试玩。现有原型尚未提交推送，不应将其标为正式完整版。

## 分阶段迁移与验收

1. **建立工程骨架**：同仓库独立迁移分支/目录；TypeScript、构建、场景流、统一16:9和输入。验收任意窗口比例都不拉伸，进入/退出场景不残留监听器。
2. **封面到大厅**：正式主视觉、登录/注册、真实加载反馈、一个动态角色和完整悬浮/切换反馈。先验收视觉品质，不继续批量做页面。
3. **练习场样板**：一角色、基础射击、三弹种、近战、完整技能条与能量、伤害/击穿反馈、引导。要求手感与可读性过关。
4. **双人关卡样板**：战前准备 → 合作机关 → 一场Boss战 → 服务器结算 → 存档；测试两台客户端、断线重连、胜负与重复奖励防护。
5. **迁移其余内容**：第二角色、树、配件、补给、十二关、画廊；逐项整合并回归，而不是同时堆叠。
6. **本地完整验收后再部署**：用户服务器/域名明确后配置HTTPS、WebSocket、数据库持久化和备份；部署不属于当前已授权的立即工作。

## 备选引擎

Godot可导出Web，若未来优先考虑桌面客户端/3D、可视化场景编辑工作流，可以再评估。当前已积累JS服务端和共享规则，且目标是浏览器2D游戏，Phaser迁移成本更低。Unity或3D引擎暂未看到足够收益，不为“更像游戏”而增加体积和工作流负担。
